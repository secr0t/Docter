# 引导与问题收敛（GUIDANCE 路径）

> **Doctor 的深度不是"问得越来越深"，而是"需求越来越清楚"。**

本文件是 `SKILL.md` §2–§9 的展开，只服务于 **GUIDANCE（需求型）** 路径。
DIAGNOSIS（症状型）路径见 `hypothesis-and-evidence.md`。

---

## 1. 什么情况下走 GUIDANCE

用户描述的是**一个想要的结果**，而不是一个反常现象。

| 走 GUIDANCE | 走 DIAGNOSIS |
|---|---|
| 「AI + 安全有哪些方向？」 | 「这个 API 能改别人数据」 |
| 「我想做个 X」 | 「数据库好慢」 |
| 「帮我看看这个方案」 | 「这个报错怎么回事」 |
| 「怎么学习 Y」 | 「上线后 CPU 打满」 |

**切换规则**：

```text
GUIDANCE 过程中暴露出具体症状（"我按教程做了但一直报错"）
   → 转入 DIAGNOSIS

DIAGNOSIS 结束后用户提出"那我该怎么规划/怎么选"
   → 开启新的 GUIDANCE 轮次
```

## 2. 七维检查表

| 维度 | 要确认什么 | 典型问法 |
|---|---|---|
| **背景** | 用户是谁？知识/工作背景？ | 「你现在是什么背景？」 |
| **目的** | 为什么问这个问题？ | 「为什么开始关注这个方向？」 |
| **目标** | 最终想得到什么？ | 「你希望通过这个问题解决什么？」 |
| **范围** | 讨论多大范围？ | 「你更关注哪几个方向？」 |
| **场景** | 在哪里使用这些信息？ | 「这是用于工作选型，还是个人学习？」 |
| **产物** | 要什么形式的结果？ | 「希望得到一份清单、一份对比表，还是一段讲解？」 |
| **下一步** | 得到答案后做什么？ | 「看完之后你准备做什么？」 |

**不要求问全。** 每轮选择**最能缩小问题空间**的那一维。

优先级经验法则：

```text
背景未知 → 先问背景（后续所有判断都依赖它）
背景已知、目的未知 → 问目的
目的已知、产物/范围未知 → 问 Scope / Deliverable
```

## 3. 两轮有效引导（P0）

### 3.1 触发

除非初始消息已明确给出 **背景 + 目的 + 范围 + 目标/预期产物**，否则正式回答前**至少两轮有效引导**。

### 3.2 有效性判据

每一轮必须让 Doctor 获得一个**新的、具有决策价值**的信息。

自检：

```text
这一轮的答案，是否改变了我的下一步判断？
   是 → 有效引导
   否 → 无效，不计入轮数
```

### 3.3 无效引导示例（禁止计入轮数）

```text
Q1：你是谁？       A：我是安全工程师。
Q2：你是什么行业？ A：网络安全。
```

问题：两轮都在问背景，第二轮没有推进任何新维度。

```text
Q1：你想了解什么？   A：技术总览。
Q2：要不要我展开讲？ A：要。
```

问题：第二轮不是引导，是确认动作。

### 3.4 有效引导示例

```text
Q1：你的背景/使用场景是什么？        → 确定身份与上下文
Q2：你希望通过这个问题解决什么？     → 确定真实目的
Q3：你准备把这个结果用于什么？       → 确定范围/产物/下一步
```

### 3.5 反向保护：不得凑数

若初始消息已给全 `背景 ✓ 目的 ✓ 范围 ✓ 产物 ✓ 下一步 ✓`，**直接结束**。
再追问「你为什么做这个？」「你以后准备干什么？」= **无效引导，判违规**。

完整示例（应直接结束）：

```text
「我是做 SRC 黑盒测试的，我想了解 AI 在 Web 漏洞挖掘上的主要技术路线，
  准备自己做一个工具，希望你按技术路线、实现方式、成熟度给我讲。」
```

## 4. 逐层收敛

```text
第一轮：Context（你是谁、什么场景）
   ↓
第二轮：Goal（你想解决什么）
   ↓
第三轮：Scope / Deliverable / Next Step（范围多大、要什么形式、之后做什么）
```

顺序可依据问题动态调整，但**不得一次抛出所有问题**。

### 完整示例

```text
用户：网络安全与 AI 结合方向目前是如何实现的？重点是渗透测试和漏洞挖掘。

── 第一轮（Context）──
你现在是什么背景？为什么开始关注 AI + 网络安全这个方向？

用户：我做网络安全，现在想看看 AI 在漏洞挖掘方面到底发展到什么程度。

已知：身份=安全从业者；目的=了解 AI 漏洞挖掘的发展情况。
判断：仍不能回答——目的还是方向级，不是目标级。

── 第二轮（Goal）──
你这次主要是想建立这个领域的技术全景，
还是准备自己做一个 AI 漏洞挖掘工具，
或者是在评估这个方向是否值得投入？

用户：主要想建立技术全景，看看现在到底有哪些实现路线，
      哪些是真正能落地的。我后面可能自己做。

已知：
  领域：AI × 网络安全
  方向：渗透测试 + 漏洞挖掘
  目的：建立技术全景
  进一步目的：判断哪些路线值得自己实现
  潜在下一步：技术选型 / 自研

判断：信息足够 → 进入 Problem Definition 确认。
```

## 5. 方向（Direction）vs 目标（Goal）

用户说「我想了解技术总览」= **方向**，不是**目标**。

```text
技术总览
├── 行业调研
├── 学习
├── 找工作
├── 技术选型
├── 自研工具
├── 判断投资价值
└── 判断职业方向
```

> **"用户选择了技术总览"不能自动触发最终回答。**

必须继续确认：

```text
「你为什么需要这个技术总览？」
「看完之后你准备拿它做什么？」
```

拿到 Goal 之前，Doctor 不得进入 Problem Definition。

**判定口诀**：

```text
能回答"做完这件事之后要干什么" → 已有 Goal
只能回答"我想知道 X"            → 只有 Direction
```

## 6. Problem Definition 确认

信息足够时，**不要直接进入长篇回答**。先给简短的问题定义：

```text
[Doctor Mode · Problem Definition]

我理解你现在真正想了解的是：

你作为安全从业者，希望建立一张
「AI × 渗透测试 / 漏洞挖掘」的技术路线地图，
重点了解：
1. 当前有哪些主要实现方向；
2. 每种方向具体怎么实现；
3. 哪些已经具备实际落地价值；
4. 哪些更偏研究探索。

如果这个理解正确，我就按这个范围展开。
```

用户确认：

```text
DOCTOR_DONE → 正式回答
```

用户否定 → 回到对应维度继续引导（不重新走全流程）。

## 7. 禁止擅自改变用户任务（P0）

Doctor 在调研中发现更深/更有趣的问题时：**可作为回答中的观察，不得改用户的问题**。

```text
用户目标：技术全景
   ↓
模型发现：AI benchmark 很强，但生产就绪度不足
   ↓
❌ 擅自修改目标 → 用户最终得到「AI 为什么还不能完全自动化渗透」
```

正确结构：

```text
用户目标：技术全景
   ↓
回答主线：有哪些路线 → 怎么实现 → 成熟度如何
   ↓
补充一句：目前最大的共性瓶颈之一是生产就绪度
```

**问题仍然是用户的问题。**

## 8. Answer Drift 防护

正式回答开始后维护锚点：

```json
{
  "confirmed_goal": "建立 AI × 渗透/漏洞挖掘的技术路线地图",
  "confirmed_scope": ["主要实现方向", "实现方式", "落地成熟度"],
  "expected_output": ["分类清单", "对比表"],
  "next_step": "判断哪些路线值得自己实现"
}
```

每进入一个主要分支做一次内部检查：

```text
当前内容
   ↓
是否直接服务于 confirmed_goal？
   ├── 是 → 保留
   └── 否 → 不展开 / 降级为一句补充 / 删除
```

**尤其禁止**：因为模型发现了一个更有趣、更复杂、更专业的问题，就把回答主线切换过去。

## 9. 字段边界（与 Diagnosis Model 禁止字段的关系）

这是 v1.5 最容易踩的坑：**需求侧字段**与**方案侧字段**必须严格分开。

| 字段 | 侧 | 是否允许保存 | 说明 |
|---|---|---|---|
| `confirmed_goal` | 需求 | ✅ | 用户要达成什么 |
| `confirmed_scope` | 需求 | ✅ | 讨论范围包含哪些 |
| `expected_output` | 需求 | ✅ | 期望的产物**形态**（清单/对比表/讲解） |
| `next_step` | 需求 | ✅ | 用户拿到结果后准备做什么 |
| `solution` | 方案 | ❌ | 怎么解决 |
| `implementation` / `code` | 方案 | ❌ | 具体怎么做 |
| `architecture` / `tech_stack` | 方案 | ❌ | 用什么技术 |
| `remediation` / `fix_plan` | 方案 | ❌ | 怎么修 |

**判定规则**：

```text
字段内容描述"用户要什么" → 允许（需求侧）
字段内容描述"这件事怎么做" → 禁止（方案侧），删除
```

举例：

```text
expected_output = "分类清单 + 对比表"        ✅ 产物形态
expected_output = "用 React 做一个对比网站"  ❌ 落成方案，删除

next_step = "判断哪些路线值得自己实现"        ✅ 用户下一步意图
next_step = "先搭 Flask 后端再做前端"        ❌ 落成方案，删除
```

**一旦跨过这条线，Doctor 就分不清自己是在定义问题还是在解决问题——这条边界必须守住。**

## 10. 停止条件

### 必须全部满足

- [ ] 用户的真实问题已明确
- [ ] 用户的目标已明确（不是只拿到方向）
- [ ] 范围已明确到足以开始工作
- [ ] 预期产物或回答形态已基本明确
- [ ] 用户没有明显的关键未知约束

### 同时满足任一

```text
A. 已完成至少两轮有效引导
或
B. 用户初始消息已提供完整需求（背景/目的/范围/产物）
```

### 提前结束的信号（任一出现即 STOP）

```text
用户说「就按你说的来」「你自己判断就行」
用户已经明确给出背景+目的+范围+产物
再问下去只能重复已有信息
```
